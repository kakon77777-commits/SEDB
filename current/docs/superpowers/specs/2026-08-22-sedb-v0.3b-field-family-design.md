# SEDB v0.3B — Semantic Field Family Kernel Design

**Date:** 2026-08-22  
**Status:** Approved architectural continuation of v0.3A  
**Branch:** `local-v0.3b`

## Goal

Extend pairwise semantic candidates into auditable multi-field family proposals without treating graph connectivity as synonymy and without mutating canonical field identity or sparse cell placement.

## Core invariant

$$
\boxed{\text{Pairwise Similarity}\not\Rightarrow\text{Family Truth}}
$$

and, even after review:

$$
\boxed{\text{Confirmed Family}\not\Rightarrow\text{Automatic Merge / Alias / Cell Migration}}
$$

## Architecture

The v0.3B path is deliberately three-stage:

$$
\text{Pairwise Evidence}
\rightarrow
\text{Immutable Family Proposal}
\rightarrow
\text{Explicit Review}
\rightarrow
\text{Reviewed Field Family}.
$$

Pairwise scoring reuses v0.2B deterministic `score_field_pair`. Candidate expansion is bounded. Formal family creation requires an explicit governance decision.

## Data model

### `field_family_proposals`

Immutable candidate-family header:

- `id`
- `namespace`
- `policy_version`
- `seed_field_id`
- `member_count`
- `min_pair_score`
- `avg_pair_score`
- `basis_sha256`
- `parameters_json`
- `evidence_json`
- `created_at`

### `field_family_proposal_members`

Immutable proposal membership:

- `proposal_id`
- `field_id`
- `ordinal`
- `seed_score`
- `min_peer_score`
- `avg_peer_score`
- `evidence_json`

### `field_family_reviews`

One review per proposal:

- `proposal_id`
- `decision`: `duplicate_family`, `related_family`, `split`, `reject`
- `reason`
- `decision_json`
- `evidence_json`
- `evaluator`
- `created_at`

`split` stores a validated partition plan but creates no formal family automatically.

### `field_families`

Reviewed family identity only:

- `id`
- `namespace`
- `family_type`: `duplicate` or `related`
- `label`
- `source_proposal_id`
- `status`: initially `active`
- `created_at`

### `field_family_members`

Canonical field membership. No aliases are inserted and no field row is rewritten.

### `field_family_events`

Append-only family governance events. v0.3B initially emits `created`.

## Candidate generation

For seed $s$, obtain a bounded neighbor set $N_k(s)$ using the existing deterministic blocking/scoring machinery. A candidate may join group $G$ only when:

1. it has the same namespace;
2. it has compatible `value_type`;
3. its score against the seed is at least `seed_threshold`;
4. its score against every existing member is at least `min_coherence`.

Thus v0.3B uses a complete-link style guard rather than transitive closure.

For group $G$:

$$
\operatorname{coh}_{\min}(G)=\min_{i<j}S(f_i,f_j)
$$

and

$$
\operatorname{coh}_{\mathrm{avg}}(G)
=\frac{1}{\binom{|G|}{2}}\sum_{i<j}S(f_i,f_j).
$$

A proposal requires at least two members.

## Registry scan

`scan_registry()` first invokes the existing bounded semantic scan, then builds seed-local proposals from those bounded pairwise candidates. It does not compute all global field pairs.

The scan is capped by:

- `limit_fields <= 10000`
- `max_neighbors <= 100`
- `max_members <= 32`
- `max_proposals <= 1000`

## Basis hash and stale review

A proposal basis includes:

- each member ID/status/updated timestamp;
- latest definition version number;
- relevant semantic candidate ID/status/score;
- semantic review ID/decision when present;
- proposal parameters and pairwise score matrix.

Before review, the basis is recomputed. If:

$$
H(B_t)\neq H(B_{review}),
$$

review is rejected as stale.

## Review behavior

### `duplicate_family`

Creates one formal family of type `duplicate`. A canonical field may belong to at most one active duplicate family in v0.3B. No alias, merge, field status transition, or cell migration occurs.

### `related_family`

Creates one formal family of type `related`. A field may participate in multiple related families.

### `split`

Requires an explicit partition covering each proposal member exactly once. The partition is stored in `decision_json`; no formal family is created automatically.

### `reject`

Stores review only.

## API / UI

Local API adds:

- `GET /api/family-proposals`
- `GET /api/family-proposals/{id}`
- `POST /api/family-proposals/generate`
- `POST /api/family-proposals/scan`
- `POST /api/family-proposals/{id}/review`
- `GET /api/field-families`
- `GET /api/field-families/{id}`

Browser UI adds a minimal **Field Families** panel for seed generation, proposal inspection, and duplicate/related/reject review. `split` remains API-first in v0.3B because partition editing requires a richer UI.

## Non-goals

v0.3B does not:

- use embeddings or an LLM;
- infer transitive synonymy;
- automatically merge canonical fields;
- automatically create aliases;
- move or rewrite sparse cells;
- resolve conflicting values across duplicate-family members;
- implement AI Field Agent behavior.

## Verification targets

- v0.3A 89-test baseline remains green;
- chain similarity does not become a duplicate family proposal;
- coherent 3–5 field sets do form a proposal;
- type/namespace conflicts are excluded;
- family proposals are SQLite-immutable;
- stale proposals cannot be reviewed;
- `duplicate_family` and `related_family` are auditable;
- `split` stores a valid partition but creates no family;
- formal family creation leaves field count/status/cells unchanged;
- 10K registry scan remains bounded and does not invoke all-pairs clustering.
